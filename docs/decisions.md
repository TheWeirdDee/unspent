# Decisions and deviations from the PRD

- Vite + React instead of Next.js: Arc Studio's runtime is Vite. API is a separate Bun service proxied through Vite in preview.
- PostgreSQL, SIWE sessions and a separate indexer were not built. Metadata is a small JSON file; request outputs are never persisted; private request data is gated by a per-request access token; activity and history are read directly from chain events (starting at the deployment block). Add Postgres + SIWE before multi-tenant use.
- `refundFor` omitted (PRD says avoid it if not needed). No early customer cancel: a reservation can be released only after expiry, per the clarified rule.
- Reservation lifetime is 20 minutes from quote; signed submission window 5 minutes. On-chain maximum lifetime is 1 day.
- Wallet UI is custom (EIP-6963 via wagmi) rather than ConnectKit, for design control. WalletConnect is not included (needs a project ID).
- Response hash only proves what the customer accepted, never service quality.
- Smart-contract wallets: the **deployed** vault takes EOA ECDSA signatures only. The contract source now accepts ERC-1271 signatures through `isValidSignature` (`_verifySignature` switches on `customer.code.length`), with every failure path mapped to `InvalidSignature`. It is not deployed; see the next two items.
- Provider nonpayment: the default stays "payment follows the customer's acceptance". The source adds an opt-in, per-reservation consent window (`providerSettleAfter`, signed inside `ReserveAuthorisation`) after which the provider's registry owner may claim up to `maxAmount` with `settleConsented` before expiry. It cannot be enabled by a provider, is capped by the reservation, and emits `ConsentSettlement` so a claim is distinguishable on chain from an acceptance. The provider still asserts delivery; nothing here proves service quality.
- Contract source is ahead of both deployments. The deployed vaults and the ABIs in `src/contracts` / `recovery/src/contracts` still describe the nine-field `ReserveAuthorisation`; a signature for one schema is invalid against the other. Deploying needs a new address, `bun run sync:deployments`, an app signing change and a fresh acceptance test. No deployment was made for this work.
- Metadata storage: one Postgres row per request plus `unspent_usage` counters, instead of a single JSON snapshot row. Counters increment in SQL and usage is written in one statement. The one-model-call lock remains process-local, so one API instance stays the supported deployment; a database-backed lock is the next step.
- Model outputs stay in memory for 30 minutes and are never persisted. That is a privacy choice, not an unfinished feature: prompts and outputs are customer content, and losing an output costs the customer nothing because payment requires their acceptance.
