## Wallet roles: what must be separate, what should be, what can be shared

The vault is adminless and enforces no relationship between these roles. Its only payout rules are that the payout wallet is not the zero address, the vault, or the USDC contract (`_checkPayout`).

| Role | What it does | MetaMask? |
|---|---|---|
| **Relayer** | Server key that pays gas for `reserveWithSignature` and `acceptAndSettle`. Cannot change signed amounts or destinations. | **No: must be its own account.** The key sits in Render's environment, so it must never be a wallet you use personally. **Required separation.** |
| Deployer | Sends the one deployment transaction. Has **no** special rights afterwards (no owner, pause or upgrade). | Yes |
| Provider owner | Calls `registerProvider`; later can change the payout wallet or deactivate the provider (never blocks refunds or releases). | Yes |
| Payout wallet | Receives settled payments. Needs no gas; never signs in this demo. | Any address you control |
| Demo customer | Approves, deposits, signs reservations and acceptance, refunds. | Yes |

- **Required:** the relayer is separate from every other role. Nothing else is technically required to differ.
- **Recommended:** the customer is a different address from the provider owner and payout, so the proof shows a customer actually paying a distinct provider.
- **Allowed for this small demonstration:** deployer = provider owner = payout wallet (one MetaMask account, "UNSPENT Owner"), and a second account as the customer. If you used a single account for everything, the demo would still move real USDC through the contract but the 0.10 payment would return to the same address, which proves less.

**Recommended setup: 2 MetaMask accounts plus the relayer = 3 addresses.**

To create the accounts in MetaMask: click the account name at the top, choose **Add account or hardware wallet**, then **Add a new account** (an Ethereum account), name it (for example "UNSPENT Owner"), and repeat for "UNSPENT Customer". Both are new accounts under the seed phrase you already have; MetaMask does not ask for a new one. Click an account's address to copy it. You may instead use an existing account (for example the testnet one, `0xE306…cab6`) as the customer: addresses are the same on every network. **Never send a seed phrase or private key to anyone, including in this chat.** Only the public `0x…` addresses are needed.

## Hosting changes after deployment

1. `deployments.json` → `mainnet`: `vault`, `deploymentBlock`, `deploymentTx`, `providerId`, `providerOwner`, `providerPayout`, `providerMetadata`; then `bun run sync:deployments` (writes `src/contracts` and `recovery/src/contracts`); rebuild and redeploy both the app and the recovery client from that commit.
2. **API (Render):** a **separate** service for mainnet (`NETWORK=mainnet`, `MAINNET_RELAYER_KEY`, `LLM_*`, its own `DATABASE_URL`, `CORS_ORIGINS` = the app's origin). The testnet service should be suspended while it runs: Render's free tier gives 750 instance hours a month across services.
3. **App (Vercel `unspent`):** `VITE_NETWORK=mainnet` and `VITE_API_BASE` = the mainnet API URL are baked in at build time, so switching the existing project takes the testnet app offline. Recommended: tag the current commit as the testnet final, switch the existing project (keeps the same domain and the MetaMask review), and rely on the recovery client, which has a network selector, for testnet. The alternative, a second project, means a new domain that will probably be flagged again.
4. **Recovery (Cloudflare Pages `unspent-recovery`):** rebuild with `npm ci && npm run build` in `recovery/` with the commit SHA set, upload, and confirm the live build stamp equals the approved commit.
5. Then, with real mainnet receipts: update `/proof`, the documentation and the submission video. No mainnet claim is made anywhere until those receipts exist.
